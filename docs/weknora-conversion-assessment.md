## 1. 结论摘要

当前结果可以证明文本层 PDF 的快速处理链路已经打通，但还不能作为 Prism 中的默认 PDF 转可编辑 Word 方案。

本次转换的主要问题不是 OCR 字符识别，而是 PDF 到 Word 的结构恢复失败：

- 标题、章节和正文的阅读顺序不可靠；
- 源 PDF 中的表格全部被展平成普通文本；
- 输出 DOCX 不包含实际的 Word 表格对象；
- 项目符号没有被保留为 Word 列表；
- 顶层章节标题没有稳定地成为独立标题；
- 输出虽然也是 7 页且可以被 Word 打开，但页数相同主要来自当前分页策略，不能证明版式保真。

因此，当前产物适合作为“文本层快速路线已完成”的性能样本，不适合作为“结构化可编辑 Word 转换成功”的质量样本。

## 2. 检查范围与方法

本次检查同时分析了源 PDF、用户提供的桌面 DOCX，以及项目 QA 目录中的对应输出，包含以下内容：

1. PDF 元数据、页面尺寸、文本层和每页文本量；
2. PDF 文本提取顺序及文本块坐标；
3. PDF 中的表格边框、行、列和单元格；
4. DOCX 的段落、标题、列表、表格和 OOXML 结构；
5. DOCX 使用 Microsoft Word 渲染后的页面图像；
6. 项目现有单元测试和任务阶段日志。

项目现有测试使用 unittest 执行，24 个测试全部通过。测试通过说明服务、Worker、基础路由和基础导出链路正常，但现有测试尚未覆盖真实文档的阅读顺序、复杂表格恢复和视觉版式。

### 3.1 源 PDF 的结构特征

源 PDF 是 Typora 生成的 7 页 A4 文字型 PDF，页面均有完整文本层，没有嵌入图片、表单、JavaScript 或加密限制。

- 1 个文档标题；

- 9 个表格；
- 75 行表格数据；
- 约 255 个表格单元格；
- 多处项目符号和编号列表。

这说明该样本非常适合验证“完整文本层 PDF 的结构化转换”，而不是 OCR 字符识别。

转换结果的主要结构指标如下：

## 4. 主要问题及根因

### 4.1 使用 PDF 内容流顺序代替视觉阅读顺序

当前文本路线在 pdf_routing.py 中使用普通的 pypdf 文本提取。PDF 内部并不保证文字对象按照人眼阅读顺序存储。表格、标题、页眉和正文可能按照绘制顺序交错存储，因此会出现：

- 表格先出现，标题后出现；
- 左列和右列交叉；
- 表格行被拼接；
- 章节标题进入前一个段落；
- 多栏内容顺序错误。

尝试使用 pypdf 的 layout 模式后，标题顺序有所改善，但仍然无法恢复 Word 表格，也不能单独解决列表和分页问题。因此，仅替换提取模式不能解决整体问题。

### 4.2 文本路线没有 PDF 几何表格识别

当前导出器的 _add_table 逻辑主要处理 PaddleOCR 返回的 HTML 表格。OCR 路线可以将 HTML 表格写入 Word，但完整文本层 PDF 直接走文本路线时，没有对应的 PDF 几何表格检测。

因此源 PDF 中的表格边框、行列坐标和单元格边界没有进入 DOCX 模型，最终只能把表格内容按文本流拼接。

### 4.3 标题识别规则不覆盖当前章节格式

源文档使用以下形式的顶层标题：

~~~text
1. 测试范围
2. 前置条件
3. 论文解析结果
4. 检索测试结果
~~~

当前规则能够处理部分中文数字标题和 4.1 形式的小节，但没有稳定覆盖 ^\d+\.\s+ 形式的顶层标题。这些标题可能被识别为正文、编号项，或者和前后的表格文本合并。

此外，当前逻辑以“提取结果的第一行”作为标题判断依据。当 PDF 默认提取结果第一行是“项目 内容”时，就会把错误的内容设置成标题。

### 4.4 项目符号不能只依赖文本字符恢复

源 PDF 中的项目符号没有稳定出现在文本提取结果中，可能是独立矢量绘制对象或特殊字体符号。当前逻辑依赖 •、- 等字符识别列表，因此无法恢复这类项目符号。

仅增加正则表达式不足以解决问题，还需要结合文本行横坐标、相邻行缩进、行间距和列表上下文进行推断。

### 4.5 文本规范化丢失布局信息

当前文本规范化逻辑会压缩空格和制表符。对于连续正文，这样做可以减少无意义空白；但对于布局恢复，会丢失：

- 表格列之间的间距；
- 列表缩进；
- 多栏位置；
- 空白行和段落间距；
- 文本块之间的空间关系。

后续实现需要同时保留用于路由的规范化文本，以及用于结构恢复的原始文本行、坐标、字号和边界框。

### 4.6 7 页结果不能作为版式正确的证据

当前文本导出路线为源 PDF 页面创建对应的 Word section，并通过页面尺寸和分页控制维持页数。这样可以让输出页数接近源文件，但不能保证表格、段落和标题在页面中的位置一致。

当前结果未出现明显裁切或重叠，但表格被展平、段落被合并、章节顺序错误，说明“文件可打开”和“页数一致”两个指标远远不够。

## 5. 改进方向

### 5.1 第一优先级：建立布局感知的中间模型

不要继续让 list[str] 直接驱动 Word 导出。建议增加统一的文档中间表示：

~~~text
Document
└── Page
    ├── TextBlock
    ├── HeadingBlock
    ├── ListBlock
    ├── TableBlock
    └── ImageBlock
~~~

每个块至少应保存：

~~~text
page_number
bbox: x0, y0, x1, y1
text
font_size
font_name
reading_order
block_type
confidence
~~~

解析层负责识别文本、表格、列表和版面；中间模型负责统一结构；Word 导出层负责将结构映射为标题、段落、列表和表格。这样可以避免每种输入路线分别维护一套互不一致的段落逻辑。

### 5.2 第二优先级：为文本层 PDF 增加几何表格检测

对于本次样本，PDF 的线条和文本坐标已经可以恢复 9 个表格。建议引入 pdfplumber 或等价的 PDF 几何解析能力：

1. 检测水平线、垂直线和文本聚集区域；
2. 根据表格边界生成行列网格；
3. 识别合并单元格；
4. 根据 PDF 的列宽设置 Word 列宽；
5. 将表头设置为重复表头；
6. 关闭或限制 Word 表格的自由自动调整；
7. 处理跨页表格，避免出现孤立的末行或无表头续表。

验证阶段的探针已经证明表格语义提取是可行的，下一阶段重点应放在 PDF 坐标到 Word 表格布局的映射、列宽、行高和分页控制，而不是重新执行 OCR。

### 5.3 第三优先级：完善标题和列表识别

标题规则至少需要区分：

~~~text
^\d+\.\s+        # 顶层章节，如 1. 测试范围
^\d+\.\d+\s+     # 二级小节，如 4.1 检索结果汇总
~~~

但不应只依赖正则。建议综合判断：

- 字号是否明显大于正文；
- 字体是否加粗；
- 文本块是否位于正文左边界；
- 前后是否存在较大的垂直间距；
- 是否位于表格之外；
- 章节编号是否连续。

列表应综合判断左缩进、相邻行横坐标、行间距、连续编号、项目符号附近的文本和列表上下文。同时应排除章节标题、表格内编号、URL、版本号和普通正文中的数字开头句子。

### 5.4 第四优先级：分离文本层质量与转换质量

“存在完整文本层”只能说明文件不需要 OCR，不能说明文件适合直接转换为结构化 Word。建议在任务结果中增加：

~~~text
text_layer_confidence
reading_order_confidence
table_detection_confidence
heading_detection_confidence
layout_confidence
editable_level
visual_fidelity
warnings
~~~

本次文件可以被描述为：

~~~text
route: text_layout
ocr_required: false
text_layer_confidence: high
layout_confidence: medium
table_count: 9
editable_level: best_effort
warnings:
  - detected_tables_require_semantic_export
  - source_bullets_may_be_vector_markers
~~~

这样可以避免仅因为文本层完整，就将结构明显复杂的 PDF 误标记为高质量转换结果。

### 5.5 第五优先级：明确输出目标

PDF 转 Word 至少有三个不同目标，不能用一个默认路线同时满足：

| 输出目标 | 推荐实现 | 特点 |
| --- | --- | --- |
| 视觉保真 | 每页作为 Word 图片 | 版式最接近原 PDF，但不可编辑 |
| 结构可编辑 | 文本、标题、列表、表格语义化导出 | 可编辑，但可能发生分页重排 |
| 混合模式 | 页面图像加可编辑内容 | 适合低置信度文档，但需要明确用户看到的结果 |

当前 hybrid 路线更接近页面图像和可编辑文本的组合，不应让用户误以为它是同一页面上的可编辑叠加层。产品层应明确显示输出类型和可能的分页变化。

## 6. 推荐路由矩阵

| PDF 特征 | 推荐路线 |
| --- | --- |
| 完整文本层、无表格、单栏 | 布局感知的文本 DOCX |
| 完整文本层、存在表格 | 布局感知的语义 DOCX，并输出真实 Word 表格 |
| 文本层缺失或不完整 | OCR 或页面图像 |
| 多栏、旋转、复杂合并表格 | 低置信度语义转换或混合模式 |
| 视觉保真优先 | 页面图像型 DOCX |
| 可编辑性优先 | 允许页数和局部版式发生变化的结构化 DOCX |

本次 WeKnora 文档应进入“完整文本层、存在表格”的第二类，而不是直接使用当前的简单文本路线。

## 7. Prism 集成建议

建议保留当前的 API 与 Worker 分层：

- Prism/Tauri 负责上传文件、启动任务、查询进度和下载结果；
- PDF 解析和 OCR 放在独立 Worker 中；
- 不要将 PaddleOCR 模型直接加载到 Tauri 前端或主进程；
- 任务结果返回路线、置信度、警告和可编辑性级别；
- 允许用户选择“视觉保真”或“可编辑优先”；
- 对复杂文档不要静默输出一个看似成功、实际结构严重错误的 DOCX。

建议向 Prism 暴露类似以下结果信息：

~~~json
{
  "route": "text_layout",
  "status": "succeeded",
  "editable_level": "semantic_best_effort",
  "layout_confidence": 0.78,
  "page_count": 7,
  "table_count": 9,
  "warnings": [
    "部分项目符号可能来自 PDF 矢量标记",
    "复杂表格可能发生分页重排"
  ]
}
~~~

## 8. 验证项目改进建议

### 8.1 回归样本

建议将本次 WeKnora 文档保留为固定回归样本。如果仓库不适合长期保存原始论文报告，可以保存脱敏后的等价结构样本，但必须保留标题、列表、普通表格、跨页表格和 API 表格等结构特征。

建议验收指标如下：

- 页数：7 页；
- 页面尺寸：A4；
- 表格数量：9；
- 表格总行数：75；
- 表格单元格数量：约 255；
- 标题和章节数量：标题加 14 个编号章节或小节；
- 标题出现在正文开头；
- 顶层标题不得进入编号列表；
- 项目符号不得全部退化为普通正文；
- 不得出现吞并多个表格行的超长段落；
- Word 文档实际表格数不得为 0。

### 8.2 自动化测试

建议增加以下测试类型：

1. 文本层 PDF 的视觉阅读顺序测试；
2. 顶层标题和二级标题识别测试；
3. 项目符号、编号列表和表格内编号区分测试；
4. 表格数量、行数、单元格内容和合并关系测试；
5. Word 原生 w:tbl 结构测试；
6. 表头重复、跨页表格和列宽测试；
7. DOCX 渲染后的页数、空白页、截断和关键区域测试；
8. 低置信度时切换到页面保真或增强路线的测试。

DOCX 不能只通过 ZIP/OOXML 完整性和文本字符数量验收，必须同时进行语义检查和渲染检查。

### 8.3 样本集

至少准备以下类型的真实或脱敏样本，每类不少于 10 份：

- 中文文字型报告；
- 清晰扫描文字 PDF；
- 低清晰度或倾斜扫描件；
- 多栏报告和带页眉页脚的文档；
- 普通表格与跨页表格；
- 图文混排、图表和公式文档；
- 大页数论文或长报告；
- 项目符号由矢量对象或特殊字体绘制的 PDF。

每份文件应记录：路线、页数、文件大小、总耗时、P50/P95 耗时、失败率、字符错误、阅读顺序、表格结构、视觉完整性和 DOCX 体积。

### 8.4 渲染检查

建议将 DOCX 经过 Microsoft Word 或 LibreOffice 渲染为 PDF 后再检查：

- 页面数量；
- 是否出现额外空白页；
- 标题位置；
- 表格是否溢出或被截断；
- 表格列宽是否稳定；
- 关键页面的感知差异或截图差异。

如果 Prism 的最终用户主要使用 Microsoft Word，验收应至少包含 Word 渲染结果；如果需要兼容 LibreOffice，则需要增加跨渲染器检查。

## 9. 实施顺序

### 阶段一：布局中间模型

1. 保留 PDF 文本行、坐标、字号和页面尺寸；
2. 建立 TextBlock、HeadingBlock、ListBlock 和 TableBlock；
3. 增加块级阅读顺序排序；
4. 将当前纯文本导出改为消费中间模型。

### 阶段二：表格与列表恢复

1. 为文本层 PDF 增加几何表格检测；
2. 输出实际 Word 表格；
3. 保留列宽、表头和合并单元格；
4. 根据缩进和上下文恢复列表；
5. 修正顶层章节和二级小节识别。

### 阶段三：质量门禁与回归

1. 将“文本层完整”和“结构转换合格”拆成两个判断；
2. 增加布局置信度和警告；
3. 加入本次 WeKnora 文档回归测试；
4. 增加 Word/LibreOffice 渲染检查；
5. 建立批量样本基准。

### 阶段四：Prism 集成

1. 先接入状态查询、结果下载和错误展示；
2. 暴露路线、质量等级和警告信息；
3. 提供视觉保真和可编辑优先选项；
4. 在复杂文档上使用增强路线或混合模式；
5. 通过批量基准后再确定默认路线和服务器资源配置。

## 10. 最终判断

当前项目已经具备以下基础能力：

- 能识别完整文本层 PDF；
- 能避免对文字型 PDF 执行不必要的 OCR；
- 能快速生成可打开的 DOCX；
- Worker、状态持久化和失败重试链路基本可用。

但在进入 Prism 集成前，必须优先补齐：

1. 布局感知的 PDF 中间模型；
2. 文本层 PDF 的表格检测和真实 Word 表格导出；
3. 顶层标题和项目符号识别；
4. 阅读顺序校正；
5. 面向真实样本的结构和视觉验收；
6. “文本层完整”与“转换质量合格”的质量门禁分离。

如果按投入产出排序，最值得先做的是“布局模型、表格恢复和回归验收”。这三项完成后，本次文档才有可能从“文本存在但结构不可用”提升到“基本可编辑、结构可维护”的水平。
