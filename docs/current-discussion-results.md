# PDF 转 Word 当前讨论结论

**整理日期：** 2026-08-31

**适用范围：** `D:\pdf_validation` 独立验证仓库及第一版服务器服务
**当前目标：** 在不依赖用户电脑 GPU 的前提下，使用服务器模型为不同类型的 PDF 提供稳定的 PDF 转 Word 服务，并使大多数常见文件的处理时间控制在 1 分钟以内。

## 一、核心结论

1. **不能使用单一路线处理所有 PDF。** PDF 至少应按文本层、扫描图像、版面复杂度和编辑需求自动分流。
2. **轻量 OCR 可以作为默认路线，但不应全局关闭所有辅助模块。** 普通、横向、清晰文字的字符识别通常不会大幅下降；旋转、倾斜、多栏、表格、图表和公式的结构质量会明显受影响。
3. **“视觉完整”和“可编辑结构”是两个目标。** 当前混合导出模式保留页面图像，同时附加 OCR 文本，能够避免页面内容缺失；但 OCR 附录不等同于完整的 Word 原生排版。
4. **VL 或完整 PPStructureV3 不适合作为 CPU 默认路线。** 它们可以改善复杂版面或内容恢复质量，但在当前 CPU 环境下耗时和内存成本较高，应作为按需增强路线。
5. **要达到一分钟目标，关键是减少不必要的推理。** 文本层 PDF 应优先直接提取文本，纯图片型展示文档在不要求可编辑时应直接保留页面图像，只有需要 OCR 的页面才进入识别队列。
6. **正式服务必须将推理移出 API 进程。** 当前原型在 CPU 推理期间可能造成状态接口延迟；生产部署应采用 API、任务队列和独立 worker 分离的结构。

## 二、已完成的验证与实际数据

以下数据来自当前独立验证，不是理论估算。时间受机器性能、模型缓存和并发状态影响，不能直接视为服务器承诺值。

| 路线或样本 | 结果 | 实际观察 |
| --- | --- | --- |
| `structure-lite`，两页合成文字样本 | 成功 | 模型缓存后约 34 秒；未启用表格结构识别 |
| `structure-table-lite`，单页 4×4 表格 | 成功 | 模型缓存后约 42 秒；16 个单元格正确，DOCX 含真实 Word 表格 |
| `structure-table-lite`，真实日报 | 成功 | 首次服务端到端约 145 秒；早期文字导出文件约 38 KiB |
| 文本层快速路线，真实日报 | 成功 | 文本层分析约 0.131 秒，DOCX 导出约 0.034 秒，总耗时约 0.165 秒；未加载 OCR 模型 |
| VL，两页文字和表格 | 成功 | 初始化约 73 秒，CPU 推理约 324 秒 |
| VL，真实日报两页 | 成功 | CPU 推理约 939 秒；正文和编号列表基本完整，但交互式体验不可接受 |
| 混合模式，9 页图片型 PDF | 成功 | 端到端约 201 秒；生成 DOCX 约 1.32 MiB，包含 9 个页面图像和 OCR 文本页 |
| 完整 `PPStructureV3` | 不建议作为默认 | oneDNN 路径出现 CPU 属性转换错误；关闭 oneDNN 后资源占用约 7 GiB，未在可接受时间内完成 |

### 对数据的解释

- 当前实测尚未证明“所有 PDF 均能在一分钟内完成”。
- 真实日报已验证文本层快速路线可在远低于 1 分钟的时间内完成，但这只代表文本层清晰可提取的文件，不代表扫描件和复杂 PDF。
- 现有耗时主要来自模型初始化和逐页 CPU 推理，DOCX 写出本身不是主要瓶颈；混合模式测试中 DOCX 导出约 0.9 秒，而推理约 177 秒。
- 对文字型 PDF，若存在可用文本层，直接提取文本的速度通常会远低于 OCR；当前服务若仍强制走 OCR，就无法达到合理的批量处理效率。
- 对图片型 PDF，若只要求 Word 中视觉内容完整，保留页面图像可以跳过 OCR；若要求可编辑文本，则必须接受 OCR 成本，或将其放入慢速队列。

## 三、轻量路线对准确率的影响

轻量路线的影响应拆分为“字符识别准确率”和“版面结构恢复质量”两部分。关闭辅助模块并不一定会让每个字符都大幅变错，但会降低特定文档类型的整体可用性。

| 模块 | 普通横向文字 | 关闭后的主要风险 | 建议 |
| --- | --- | --- | --- |
| 文本检测与识别 | 核心能力保留 | 低清晰度、粘连字和复杂背景仍可能误识别 | 默认启用 |
| 文档方向分类 | 通常影响较小 | 旋转页面可能整体识别失败或阅读顺序异常 | 检测到旋转时启用 |
| 去畸变 | 平面、清晰页面影响较小 | 拍照、弯曲页面、透视变形的字符准确率下降 | 对扫描/拍照件按需启用 |
| 文本行方向分类 | 横向文本影响较小 | 竖排、局部旋转或混排文本漏检、错检 | 检测到非横向文字时启用 |
| 版面检测 | 字符可能仍可识别 | 多栏、页眉页脚、标题、阅读顺序和区域归属变差 | 多栏或复杂版面启用 |
| 表格识别 | 单元格文字可能仍存在 | 行列关系、合并单元格和可编辑表格丢失 | 表格页启用；否则保留页面图像 |
| 图表识别 | 图中少量文字可能被识别 | 数据关系、图例和图表语义无法恢复 | 以页面图像保真为主，按需增强 |
| 公式识别 | 普通文字识别仍可用 | 公式可能被识别为普通字符，无法得到可靠公式结构或 LaTeX | 公式页保留图像或进入增强路线 |

因此，轻量路线可以接受，但前提是采用**按页面或按文档类型的条件启用**，而不是对全部文件无差别关闭模块。当前混合导出模式下，原始页面图像仍保留视觉内容，所以辅助模块关闭主要影响 OCR 可编辑部分，不会改变页面图像本身的完整性。

## 四、建议采用的通用处理架构

### 4.1 自动分流

处理入口先读取 PDF 元数据和页面特征，再决定路线：

```text
上传文件
  ├─ 安全校验：扩展名、MIME、文件头、大小、页数、解密状态
  ├─ 快速分析：是否有文本层、页面尺寸、文字密度、图像占比、旋转角度
  └─ 路由
       ├─ 文本层清晰 PDF       → 直接提取文本并生成 DOCX
       ├─ 图片型但不要求编辑   → 页面图像保真导出
       ├─ 普通扫描文字 PDF      → 轻量 OCR 快速路线
       ├─ 多栏/表格/公式/旋转   → 按需启用模块或进入增强路线
       └─ 低置信度或超时        → 慢速队列或返回可下载的保真结果
```

### 4.2 推荐的处理路线

| 路线 | 适用文件 | 默认处理 | 目标 |
| --- | --- | --- | --- |
| 快速文本路线 | 有文本层、普通报告、电子生成 PDF | `pypdf`/文本层提取，保留段落和分页 | 大多数文件数秒至十几秒 |
| 页面保真路线 | 扫描件、演示文稿、图文混排且不强求编辑 | 页面图像压缩后写入 DOCX | 快速完成且视觉不缺失 |
| 轻量 OCR 路线 | 清晰扫描文字、少量旋转 | 低分辨率渲染，启用基础检测识别，按需启用方向处理 | 争取控制在 1 分钟内 |
| 增强路线 | 多栏、复杂表格、公式、低置信度页面 | 结构识别或 VL，限制并发和资源 | 质量优先，允许较长等待 |

增强路线不应阻塞快速路线，也不应与 API 进程共享同一执行上下文。

## 五、达到“一分钟以内”的优化重点

### 第一优先级：减少无效 OCR

- 先检测文本层；文本层可用时不要重复渲染和 OCR。
- 纯图片型 PDF 根据用户需求选择“页面保真”或“可编辑 OCR”，不要默认两者同时执行。
- 对同一文件使用 SHA-256 缓存，重复上传直接返回已有结果。
- 对扫描件先做低成本页面分类，只对疑似文字页 OCR，空白页和纯装饰页跳过。

### 第二优先级：控制单页计算量

- 快速路线使用统一的像素上限，而不是无限提高 DPI。
- 对普通文字扫描件优先测试 150–200 DPI；低置信度页面再局部升档。
- 限制单页最大像素、总页数、总像素和并发任务数。
- 页面图像输出使用可配置的 JPEG 质量和像素上限，避免 DOCX 体积无界增长。

### 第三优先级：减少模型和进程开销

- worker 启动时预加载并复用模型，避免每个任务重复初始化。
- API 进程只负责认证、上传、查询和下载；OCR 在独立 worker 中执行。
- 使用有界队列和明确的超时；不要通过无界增加 Uvicorn worker 数量来提高吞吐。
- 在服务器上监控内存、CPU、队列长度、单任务耗时和失败原因，再决定并发度。
- 当前已观察到 oneDNN 在此 CPU 环境存在兼容性风险，启用前必须单独压测和验证。

## 六、第一版服务器必须具备的稳定性措施

### 资源边界

- 上传大小上限：当前默认 50 MiB。
- 页数上限：当前默认 100 页。
- 页面像素上限：混合模式当前默认 4 MP，可通过环境变量调整。
- 任务文件 TTL 清理：当前默认 3600 秒。
- 任务队列设置最大长度，队列满时快速返回可理解的错误，而不是继续占用内存。

### 安全边界

- 不直接暴露 PaddleOCR 管理端口；API 前置反向代理并启用 HTTPS。
- 使用 Bearer Token 或 `X-API-Key`，令牌放在服务器环境变量或密钥管理系统中。
- 校验 PDF 文件头、解析状态和加密状态，不仅依赖文件扩展名。
- 限制来源、请求体大小、上传频率和单 IP 并发数。
- 临时文件使用独立目录，任务结束或 TTL 到期后清理；日志不得记录令牌和敏感文档内容。
- worker 使用低权限用户运行，并限制可写目录。

### 可观测性

阶段日志至少应包括：

1. 上传校验开始和结束；
2. PDF 元数据读取；
3. 页面分析与路线选择；
4. 模型加载或模型复用；
5. 页面渲染；
6. OCR/结构识别的页码进度；
7. DOCX 导出；
8. 产物校验、清理和最终状态。

每个任务应带有唯一 `job_id`，并记录阶段耗时、页数、文件大小、路线、失败异常类型和资源限制触发情况。

## 七、当前代码状态

当前第一版服务已具备：

- HTTP 健康检查、任务创建、状态查询、结果下载和删除接口；
- 文本层检测和自动分流；
- 文本层 PDF 直接提取并生成 DOCX 的快速路线；
- Bearer Token 或 `X-API-Key` 认证；
- 文件大小、页数和 PDF 类型校验；
- 任务 TTL 清理；
- 阶段日志；
- `text` 与 `hybrid` 两种导出模式；
- 混合模式下的页面图像保留与 OCR 文本附录；
- 页面图像像素上限和 JPEG 质量配置；
- 基础服务测试和混合导出测试。

当前仍存在的工程问题：

- 推理仍在服务进程中执行，CPU 推理时状态接口可能延迟，尚未完成独立 worker/队列改造。
- 尚未建立覆盖真实业务文件的批量基准，无法证明大多数文件可稳定在 1 分钟以内。
- 当前自动分流是文档级别；混合 PDF 尚未实现逐页的文本/OCR 混合路线。
- 复杂表格、公式、多栏、旋转扫描件的质量边界仍需真实样本验收。
- 当前工作区还有混合模式相关未提交修改，提交前应复核测试结果和文档内容。

## 八、后续实施顺序

### 阶段 1：先实现快路径（已完成基础版本）

1. 已增加文本层检测和直接提取路线。
2. 已增加文档级路由决策和阶段日志。
3. 普通扫描件的 OCR 参数固定和快速路线时间预算仍待后续实施。
4. 页面特征分析、总像素预算和任务级超时仍待补充。

### 阶段 2：改造服务运行模型

1. API 与 worker 分进程运行。
2. 使用有界任务队列，状态持久化到 Redis 或数据库。
3. 增加 worker 崩溃恢复、超时取消和失败重试。
4. 在反向代理配置 HTTPS、请求体限制、限流和访问日志。

### 阶段 3：建立批量验收基准

至少准备以下样本类别，每类不少于 10 份：

- 文本层中文报告；
- 清晰扫描文字 PDF；
- 低清晰度或倾斜扫描件；
- 多栏报告和页眉页脚文档；
- 普通表格与跨页表格；
- 图文混排、图表和公式文档；
- 大页数论文或长报告。

记录每份文件的：路线、页数、文件大小、总耗时、P50/P95 耗时、失败率、OCR 字符错误、阅读顺序、表格结构、视觉完整性和 DOCX 体积。

### 阶段 4：按置信度启用增强

- 轻量路线输出页面级置信度和异常信号。
- 仅将低置信度页面送入表格、版面、方向或 VL 增强路线。
- 增强失败时保留页面保真结果，避免整个任务无产物。
- 根据真实基准决定是否引入更大的模型或服务器 GPU。

## 九、验收标准

在没有进一步调整硬件条件的情况下，建议将验收拆为以下指标：

1. **速度：** 普通文本层 PDF 的 P95 小于 30 秒；普通清晰扫描 PDF 的 P95 小于 60 秒。
2. **稳定性：** 100 份混合样本连续处理无服务进程崩溃；单任务超时不影响后续任务。
3. **资源：** 单任务内存和总像素受限；队列满、文件过大、页数过多时可预测地拒绝。
4. **质量：** 普通正文可读；表格、公式和多栏文件在路由到增强路线时有明确的质量结果；页面保真路线不得丢页或出现空白页。
5. **安全：** 未认证请求被拒绝；上传文件不造成任意路径写入；日志不泄露凭证和文档正文。
6. **可维护性：** 每个任务可通过 `job_id` 定位到路线、阶段耗时、错误原因和输出文件。

## 十、结论

当前方案可以继续沿着“服务器集中部署模型 + 客户端调用 API”的方向推进，但默认策略应从“所有 PDF 都做完整结构化 OCR”调整为“先分类，再选择最低成本的可接受路线”。

轻量 OCR 对普通文字的字符识别通常可接受，真正明显下降的是复杂页面的结构恢复能力。只要保留页面图像作为兜底，并根据页面特征按需启用方向、版面、表格和公式能力，就能在速度、质量和服务器资源之间取得可控平衡。

在完成文本层快路径、独立 worker、批量基准和安全边界之前，不能对“一分钟以内”和“多数文件质量可接受”作正式承诺。
